# Research: Merge Conflict Resolution

**Feature**: [005-merge-conflict-resolution](./spec.md) | **Date**: 2026-09-04

Three research subjects, gathered from the vendor's and the tool's own published documentation. Each finding carries its source. Where no authoritative source exists the gap is **stated rather than filled**, following the treatment already used in `specs/002-vendor-plugin-skills/research.md` and `specs/003-ccd-skill-rename/research.md` — a reader moving between the four artifacts meets one convention.

Findings are marked **HARD** where the documentation states the behaviour normatively, and **SOFT** where it is shown by example or described without commitment. That distinction is carried into `docs/` because it is what tells a future contributor whether a practice can be relied on or merely observed.

This artifact is the source material for the three documents under `docs/`. It is not a duplicate of them: this records what was found and where, and `docs/` states what this repository therefore does.

### 1.2 Path-scoped rules — `.claude/rules/`

This was the highest-value question of the whole pass, because clarification Q2 chose to put rules there and nothing in this repository had used the mechanism before.

| #     | Finding                                                                                                                                                                     | Strength | Source                                      |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------- |
| 1.2.1 | `.claude/rules/` is a **documented feature**, not an informal convention.                                                                                                   | HARD     | <https://code.claude.com/docs/en/memory.md> |
| 1.2.2 | Rules use YAML frontmatter with the key `paths:` — `paths`, not `path`.                                                                                                     | HARD     | <https://code.claude.com/docs/en/memory.md> |
| 1.2.3 | Glob patterns are supported, including `**/*.ts`, `src/**/*`, `*.md`, `src/components/*.tsx`, and brace expansion such as `src/**/*.{ts,tsx}`.                              | HARD     | <https://code.claude.com/docs/en/memory.md> |
| 1.2.4 | A `paths` list shares a budget of **1,000 expanded patterns and 4 MiB**; each brace group multiplies the expanded count.                                                    | HARD     | <https://code.claude.com/docs/en/memory.md> |
| 1.2.5 | A rule with `paths` applies **only** when Claude is working with matching files, not on every tool use.                                                                     | HARD     | <https://code.claude.com/docs/en/memory.md> |
| 1.2.6 | A rule file **without** a `paths` field is loaded unconditionally at launch — so omitting `paths` makes it behave like `CLAUDE.md` content and forfeits the entire benefit. | HARD     | <https://code.claude.com/docs/en/memory.md> |
| 1.2.7 | For instructions that need not be in context all the time, the documentation directs you to a skill instead, which loads only when invoked or judged relevant.              | HARD     | <https://code.claude.com/docs/en/memory.md> |

Finding 1.2.6 is the trap, and it is why FR-006a requires each rule file to declare its paths. A `paths`-less rule file looks scoped, sits in a directory named `rules`, and costs context in every session exactly as if it had been pasted into `CLAUDE.md`.

### 1.6 Substitution variables

| #     | Finding                                                                                                                                                                                                                 | Strength | Source                                      |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------- |
| 1.6.1 | `${CLAUDE_SKILL_DIR}` is "the directory containing the skill's `SKILL.md` file", for referencing "scripts or files bundled with the skill, regardless of the current working directory".                                | HARD     | <https://code.claude.com/docs/en/skills.md> |
| 1.6.2 | `${CLAUDE_PLUGIN_ROOT}` is "the plugin's installation directory", for "scripts or files bundled anywhere in the plugin, **including resources shared between the plugin's skills**". Substituted only in plugin skills. | HARD     | <https://code.claude.com/docs/en/skills.md> |
| 1.6.3 | `${CLAUDE_PLUGIN_DATA}` is a persistent data directory surviving plugin updates; also substituted only in plugin skills.                                                                                                | HARD     | <https://code.claude.com/docs/en/skills.md> |
| 1.6.4 | `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_SESSION_ID}` and `${CLAUDE_EFFORT}` are also available, as are `$ARGUMENTS`, positional `$0`/`$1`, and `$name` for arguments declared in frontmatter.                                | HARD     | <https://code.claude.com/docs/en/skills.md> |
| 1.6.5 | Substitution happens in two places: the skill's Markdown content, and `Bash(...)` rules in the `allowed-tools` frontmatter.                                                                                             | HARD     | <https://code.claude.com/docs/en/skills.md> |

**Decision taken from 1.6.1 and 1.6.2.** The two variables are documented against precisely the distinction this feature needed: own files versus shared files. So `ccd-conflict-resolve` invokes its own scripts through `${CLAUDE_SKILL_DIR}/scripts/`, while `branch-options.sh` — genuinely shared by four skills — keeps `${CLAUDE_PLUGIN_ROOT}`.

This departs from the four existing skills, which all spell out `${CLAUDE_PLUGIN_ROOT}/skills/<own-name>/scripts/`. The cost of that form is recorded in this repository's own history: feature 003 renamed five skills and touched 328 references across 40 files, because every path repeated the skill's own directory name. `${CLAUDE_SKILL_DIR}` does not repeat it. The existing four are **not** migrated here — see `plan.md`'s Structure Decision for why that is a separate change.

## 3. Merge conflict resolution

Sourced from git's own documentation at version 2.55.0, read from the installed manual pages. Where a page is quoted the citation names it; `git-merge(1)` means `man git-merge` on that version, which corresponds to <https://git-scm.com/docs/git-merge>.

### 3.1 Detecting which operation is in progress

FR-017 requires determining this rather than assuming it, and the mechanism is a per-operation reference in the git directory.

The pseudorefs are all documented in **one** place, which is not any of the operation pages: `git-rev-parse(1)`, under the `<refname>` resolution rules — "If `$GIT_DIR/<refname>` exists, that is what you mean (this is usually useful only for `HEAD`, `FETCH_HEAD`, `ORIG_HEAD`, `MERGE_HEAD`, `REBASE_HEAD`, `REVERT_HEAD`, `CHERRY_PICK_HEAD`, `BISECT_HEAD` and `AUTO_MERGE`)."

| #      | Finding                                                                                                                                                                                                                                                                  | Strength | Source                                                                                            |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- | ------------------------------------------------------------------------------------------------- |
| 3.1.1  | `MERGE_HEAD` "records the commit(s) which you are merging into your branch when you run git merge."                                                                                                                                                                      | HARD     | `git-rev-parse(1)`                                                                                |
| 3.1.2  | `CHERRY_PICK_HEAD` "records the commit which you are cherry-picking when you run git cherry-pick." `git-cherry-pick(1)` adds that it "is set to point at the commit that introduced the change that is difficult to apply."                                              | HARD     | `git-rev-parse(1)`, `git-cherry-pick(1)`                                                          |
| 3.1.3  | `REBASE_HEAD` "during a rebase, records the commit at which the operation is currently stopped, either because of conflicts or an edit command in an interactive rebase."                                                                                                | HARD     | `git-rev-parse(1)`                                                                                |
| 3.1.4  | `REVERT_HEAD` "records the commit which you are reverting when you run git revert."                                                                                                                                                                                      | HARD     | `git-rev-parse(1)`                                                                                |
| 3.1.5  | `AUTO_MERGE` "records a tree object corresponding to the state the ort merge strategy wrote to the working tree when a merge operation resulted in conflicts", and is "only written when the ort merge strategy is used (the default)."                                  | HARD     | `git-rev-parse(1)`, `git-merge(1)`                                                                |
| 3.1.6  | The probe for each is `git rev-parse --verify --quiet <REF>`. `git rev-parse --git-path <path>` is the documented way to resolve a state path, and it "takes other path relocation variables such as `$GIT_OBJECT_DIRECTORY`, `$GIT_INDEX_FILE`… into account."          | HARD     | `git-rev-parse(1)`                                                                                |
| 3.1.7  | **A documented precedence order exists**, in `git log --merge`: `<other>` is "the first existing pseudoref in `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD` or `REBASE_HEAD`. Only works when the index has unmerged entries."                                         | HARD     | `git-log(1)`                                                                                      |
| 3.1.8  | **Trap: `git merge --squash` does not set the marker.** It "does not actually make a commit, move the HEAD, or record `$GIT_DIR/MERGE_HEAD`" — so a squash merge that conflicts leaves unmerged index entries with **no** `MERGE_HEAD`.                                  | HARD     | `git-merge(1)`                                                                                    |
| 3.1.9  | GAP: `git status --porcelain=v2` carries **no field naming the operation in progress.** Its complete documented header set is `# branch.oid`, `# branch.head`, `# branch.upstream`, `# branch.ab` and `# stash <N>`. Conflicts appear only as `u` records.               | GAP      | read the porcelain v2 format section of `git-status(1)`                                           |
| 3.1.10 | GAP: `.git/rebase-merge/` and `.git/rebase-apply/` are documented in **no** git manual page. `git-rebase(1)` names the two backends "apply" and "merge" but never their state directories, and `gitrepository-layout(5)` documents none of the in-progress state at all. | GAP      | searched every `man1`, `man5` and `man7` page for `rebase-merge`, `rebase-apply` and `sequencer/` |
| 3.1.11 | GAP: no manual page states that testing the pseudorefs is _the_ supported way to identify the operation. 3.1.7's ordering is the closest normative statement and is scoped to that one option.                                                                           | GAP      | searched for a single command or file reporting the current operation                             |

Two findings shaped the design here. **3.1.9** killed an earlier sketch in which `conflict-preflight.sh` read `git status --porcelain=v2` to determine the operation — porcelain v2 cannot answer that question, so the refs are probed individually instead. And **3.1.7** supplied the order to probe them in: rather than inventing a precedence, the skill uses the one git itself documents for `git log --merge`.

**3.1.8 is the trap worth carrying into the docs.** A conflicted squash merge has no `MERGE_HEAD`, so a naive probe reports "no operation in progress" on a tree that is plainly conflicted. `conflict-preflight.sh` therefore reports the operation and the conflict state as **two independent facts**, and never infers either from the other — which is also what FR-017's "MUST NOT assume one" requires, arrived at from the opposite direction.

**3.1.10 and 3.1.11 are why the skill probes refs rather than stat-ing directories.** A reasonable implementation would test for `.git/rebase-merge/`; nothing documents that path, so it could change without notice, while `REBASE_HEAD` is documented.

### 3.2 Listing conflicted paths

| #     | Finding                                                                                                                                                                                                                                                      | Strength | Source            |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- | ----------------- |
| 3.2.1 | `git ls-files -u` shows "information about unmerged files in the output, but do not show any other tracked files (forces `--stage`, overrides `--cached`)". It emits one line per stage, so a both-modified path appears three times.                        | HARD     | `git-ls-files(1)` |
| 3.2.2 | `git diff --name-only --diff-filter=U` emits each conflicted path once, which is the form to iterate over.                                                                                                                                                   | HARD     | `git-diff(1)`     |
| 3.2.3 | `git status --porcelain=v2` prefixes unmerged entries with `u` and carries `<XY>`, the submodule state, the octal modes in stages 1, 2 and 3, the worktree mode, the three object names, and the path. A mode of `0` for a stage means that stage is absent. | HARD     | `git-status(1)`   |
| 3.2.4 | Reading the three stages of a path directly: `git show :1:<path>` is the common ancestor, `:2:` is the `HEAD` version, `:3:` is the `MERGE_HEAD` version.                                                                                                    | HARD     | `git-merge(1)`    |
| 3.2.5 | `git diff AUTO_MERGE` shows "what changes you've made so far to resolve textual conflicts" — a way to show the user their own resolution before it is committed.                                                                                             | HARD     | `git-merge(1)`    |

**Decision.** `conflict-list.sh` uses `git status --porcelain=v2` as its primary source, not `--diff-filter=U`. The reason is 3.2.3: the `<XY>` code and the three stage modes are in the same record as the path, so one invocation yields path _and_ classification. `--diff-filter=U` would give the paths and require a second pass per path to classify them.

### 3.3 Classifying a conflict

The classification is documented as a two-character code, and this table is the direct source for `data-model.md`'s closed `kind` set.

| `XY` | `git status` wording      | Maps to `kind`    |
| ---- | ------------------------- | ----------------- |
| `UU` | unmerged, both modified   | `both-modified`   |
| `AA` | unmerged, both added      | `both-added`      |
| `DD` | unmerged, both deleted    | `both-deleted`    |
| `AU` | unmerged, added by us     | `added-by-us`     |
| `UA` | unmerged, added by them   | `added-by-them`   |
| `DU` | unmerged, deleted by us   | `deleted-by-us`   |
| `UD` | unmerged, deleted by them | `deleted-by-them` |

Source: the short-format table in `git-status(1)`, which porcelain v2's `<XY>` field is documented to reuse — "A 2 character field describing the conflict type as described in the short format."

| #      | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                           | Strength    | Source                                                                                         |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | ---------------------------------------------------------------------------------------------- |
| 3.3.1  | The seven codes above are the complete documented set of unmerged `XY` values.                                                                                                                                                                                                                                                                                                                                                                    | HARD        | `git-status(1)` short-format table                                                             |
| 3.3.2  | Stage numbers are documented normatively: "During a merge, stage 1 is the common ancestor, stage 2 is the target branch's version (typically the current branch), and stage 3 is the version from the branch which is being merged." Stage 0 means resolved — "the normal one, and is the only one you'd see in any kind of normal use."                                                                                                          | HARD        | `gitrevisions(7)`, `git-merge(1)`, `git-read-tree(1)`                                          |
| 3.3.3  | `git log --merge -p <path>` shows diffs first for the `HEAD` version and then the `MERGE_HEAD` version — the documented way to show _why_ each side changed, which is what a justified recommendation needs.                                                                                                                                                                                                                                      | HARD        | `git-merge(1)`, `git-log(1)`                                                                   |
| 3.3.4  | The `XY` classification explicitly covers more than merges: "the term **merge** here also includes rebases using the default `--merge` strategy, cherry-picks, and anything else using the merge machinery."                                                                                                                                                                                                                                      | HARD        | `git-status(1)`                                                                                |
| 3.3.5  | The only **stable** conflict-type strings git documents anywhere are `git merge-tree`'s: "`<conflict-type>` is a stable string explaining the type of conflict, such as" `"CONFLICT (rename/delete)"`, `"CONFLICT (submodule lacks merge base)"`, `"CONFLICT (binary)"`, `"Auto-merging"`. | 3.3.6  | `git-merge-tree(1)` gives the closest thing to an official taxonomy of what conflict markers cannot express: "there are numerous types of conflicts not representable by conflict markers (modify/delete, mode conflict, binary file changed on both sides, file/directory conflicts, various rename conflict permutations, etc.)".                                                                                                               | HARD        | `git-merge-tree(1)`                                                                            |
| 3.3.7  | Binary handling is an attribute behaviour, not a conflict code: with the `merge` attribute unset, git will "take the version from the current branch as the tentative merge result, and declare that the merge has conflicts. The `binary` built-in driver keeps your branch's version "but leave the path in the conflicted state for the user to sort out." | HARD        | `gitattributes(5)`                                                                             |
| 3.3.8  | **GAP: git does not document which of stages 1/2/3 is present for each `XY` case.** All that is documented is "the index file records **up to** three versions". The stage-presence-to-code mapping is inferable from `git-read-tree(1)`'s collapse rules but is nowhere stated.                                                                                                                                                                  | GAP         | searched `git-status(1)`, `git-merge(1)`, `git-ls-files(1)`, `git-read-tree(1)`, `git-diff(1)` |
| 3.3.9  | GAP: `DD` (both deleted) was missing from this feature's `data-model.md` `kind` set as originally drafted. It is a real documented state.                                                                                                                                                                                                                                                                                                         | GAP → fixed | `git-status(1)`                                                                                |
| 3.3.10 | GAP: no `XY` code distinguishes a type change or a binary file. Those are properties of the content and the modes, not of the conflict code, so they must be derived separately — from the stage modes in porcelain v2 for a type change, and from a content check for binary. `T` exists in the short format as "file type changed" but is not one of the seven unmerged codes.                                                                  | GAP         | no such code in the short-format table                                                         |
| 3.3.11 | GAP: `git status`'s long-format labels — the strings a user actually sees, such as "both modified:", "deleted by us:", "Unmerged paths" — are documented nowhere. Only the two-letter codes and their table glosses are.                                                                                                                                                                                                                          | GAP         | grepped `git-status(1)` for each long-format label                                             |

Findings 3.3.9 and 3.3.10 changed the model: `both-deleted` is added, and `type-changed` and `binary` are marked as **derived** rather than reported, since `conflict-list.sh` must compute them from the mode fields and a content test.

**Finding 3.3.8 is a correction to this artifact's own earlier draft**, which asserted the stage-presence mapping as documented fact. It is not documented; it is inferable, and `data-model.md`'s `stages_present` column is therefore labelled as derived. The distinction matters because an inference that holds today can stop holding without a documentation change to point at.

Finding 3.3.11 is the reason `conflict-list.sh` parses porcelain v2 rather than `git status`'s human output, beyond the usual stability argument: the human labels are not merely unstable, they are undocumented, so there is nothing to hold git to.

Finding 3.3.5 is worth noting as a road not taken. `git merge-tree` emits genuinely stable conflict-type strings, which is more than porcelain v2's `XY` codes offer for the exotic cases in 3.3.6 — but `merge-tree` "does not read from or write to either the working tree or index", so it describes a hypothetical merge rather than the conflict the user is actually sitting in. It is the right tool for previewing and the wrong one for resolving.

### 3.4 Conflict styles

Quoted, because the three styles differ in a way that matters to explaining a conflict:

> "The default is `merge`, which shows a `<<<<<<<` conflict marker, changes made by one side, a `=======` marker, changes made by the other side, and then a `>>>>>>>` marker. An alternate style, `diff3`, adds a `|||||||` marker and the original text before the `=======` marker. The `merge` style tends to produce smaller conflict regions than `diff3` … Another alternate style, `zdiff3`, is similar to `diff3` but removes matching lines on the two sides from the conflict region when those matching lines appear near either the beginning or end of a conflict region."
>
> — `git-config(1)`, `merge.conflictStyle`

| #     | Finding                                                                                                                                                                            | Strength | Source            |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ----------------- |
| 3.4.1 | Only `diff3` and `zdiff3` show the original text — the common ancestor — alongside both sides. The default `merge` style does not.                                                 | HARD     | `git-config(1)`   |
| 3.4.2 | `zdiff3` is `diff3` minus matching lines at the edges of a conflict region, so it is strictly more readable than `diff3` at no cost in information.                                | HARD     | `git-config(1)`   |
| 3.4.3 | `git checkout --conflict=<style> -- <path>` re-materialises an already-conflicted file in a different style, so the style can be changed after the fact without redoing the merge. | HARD     | `git-checkout(1)` |

**Decision.** The skill does not change the user's `merge.conflictStyle` — that is their configuration and FR-016's spirit says not to alter what was not asked about. Where it needs the common ancestor in order to explain a conflict, it reads stage 1 directly with `git show :1:<path>` (3.2.4), which needs no configuration change, or re-materialises a single path with `--conflict=zdiff3` (3.4.3) when the user asks to see it that way. `docs/merge-conflict-practices.md` recommends `zdiff3` to the reader as a personal setting, which is advice rather than an action.

### 3.5 The ours/theirs reversal — the most important finding in this section

Quoted in full, because getting it backwards silently discards the wrong side's work:

> "When checking out paths from the index, check out stage #2 (ours) or #3 (theirs) for unmerged paths.
>
> Note that during `git rebase` and `git pull --rebase`, ours and theirs may appear swapped; `--ours` gives the version from the branch the changes are rebased onto, while `--theirs` gives the version from the branch that holds your work that is being rebased.
>
> This is because rebase is used in a workflow that treats the history at the remote as the shared canonical one, and treats the work done on the branch you are rebasing as the third-party work to be integrated…"
>
> — `git-checkout(1)`, `--ours, --theirs`

| #     | Finding                                                                                                                                                                                                                                           | Strength | Source                        |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ----------------------------- |
| 3.5.1 | Under a **merge**, `--ours` is your branch and `--theirs` is the incoming branch.                                                                                                                                                                 | HARD     | `git-checkout(1)`             |
| 3.5.2 | Under a **rebase**, this is reversed in effect: `--ours` is the branch being rebased **onto** (upstream), and `--theirs` is **your own work**.                                                                                                    | HARD     | `git-checkout(1)`             |
| 3.5.3 | The reversal is not a bug and is not configurable; it follows from rebase's model of whose history is canonical.                                                                                                                                  | HARD     | `git-checkout(1)`             |
| 3.5.4 | Stated again from the rebase side, normatively: "when a merge conflict happens, **the side reported as ours is the so-far rebased series, starting with `<upstream>`, and theirs is the working branch. In other words, the sides are swapped.**" | HARD     | `git-rebase(1)`, `-m/--merge` |
| 3.5.5 | The reversal propagates to strategy options too: `git rebase -X<option>` carries "Note the reversal of ours and theirs as noted above for the `-m` option."                                                                                       | HARD     | `git-rebase(1)`               |
| 3.5.6 | `git restore --ours/--theirs` carries the same caveat by reference, so switching from `checkout` to `restore` does not avoid it.                                                                                                                  | HARD     | `git-restore(1)`              |

**This is why FR-012 requires an explanation rather than a label.** A skill offering "take ours / take theirs" as bare options is actively dangerous under a rebase: the user reads "ours" as "my work" and gets the upstream version. So the skill must name the _branch and side in concrete terms_ — "keep the version from `main`, discarding your commit's change" — derived from the operation `conflict-preflight.sh` detected. Presenting the raw flag name would satisfy the letter of FR-012 and defeat its purpose.

### 3.7 Staging and concluding — the source for FR-017c

Quoted, because it is the direct evidence for the conflict the checklist found at CHK020:

> "Resolve the conflicts. Git will mark the conflicts in the working tree. Edit the files into shape and `git add` them to the index. Use `git commit` or `git merge --continue` to seal the deal. **The latter command checks whether there is a (interrupted) merge in progress before calling `git commit`.**"
>
> — `git-merge(1)`, HOW TO RESOLVE CONFLICTS

| #      | Finding                                                                                                                                                                                                                                                                                                                               | Strength | Source                                                                                              |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | --------------------------------------------------------------------------------------------------- |
| 3.7.1  | `git add <path>` is what marks a conflicted path resolved.                                                                                                                                                                                                                                                                            | HARD     | `git-merge(1)`                                                                                      |
| 3.7.2  | **`git merge --continue` calls `git commit`, which commits the whole index — not only the paths that were conflicted.** Anything else staged is committed with it.                                                                                                                                                                    | HARD     | `git-merge(1)`, as quoted                                                                           |
| 3.7.3  | `git rebase --continue` "restart[s] the rebasing process after having resolved a merge conflict", committing the index into the replayed commit.                                                                                                                                                                                      | HARD     | `git-rebase(1)`                                                                                     |
| 3.7.4  | `git merge --abort` reverses the merge, resetting the index to `HEAD` and cleaning up working-tree changes the merge made.                                                                                                                                                                                                            | HARD     | `git-merge(1)`                                                                                      |
| 3.7.5  | `git merge --quit` differs: it "forget[s] about the current merge in progress. **Leave the index and the working tree as-is.**" So `--quit` keeps a partial resolution and `--abort` discards it.                                                                                                                                     | HARD     | `git-merge(1)`                                                                                      |
| 3.7.6  | `git merge --no-commit` performs the merge without creating a commit, "when you want to include further changes to the merge, or want to write your own merge commit message". | 3.7.7  | **Git pre-stages the clean part of the merge for you**: "After a merge … stops because of conflicts, **cleanly merged paths are already staged to be committed for you**, and paths that conflicted are left in unmerged state."                                                                                                      | HARD     | `git-commit(1)`, MERGING                                                                            |
| 3.7.8  | **`git commit` refuses a pathname-limited commit during a merge**: "during a merge resolution, you cannot use `git commit` with pathnames to alter the order the changes are committed, because the merge should be recorded as a single commit. **In fact, the command refuses to run when given pathnames** (but see `-i` option)." | HARD     | `git-commit(1)`, MERGING                                                                            |
| 3.7.9  | Pre-existing local modifications are **not** swept in: "the local modifications you had before you started merge will stay the same and the index entries for them stay as they were, i.e. matching `HEAD`."                                                                                                                          | HARD     | `git-merge(1)`, TRUE MERGE                                                                          |
| 3.7.10 | Git also refuses to start a merge that would clobber such work: "`git pull` and `git merge` will stop without doing anything when local uncommitted changes overlap with files that `git pull`/`git merge` may need to update."                                                                                                       | HARD     | `git-merge(1)`, PRE-MERGE CHECKS                                                                    |
| 3.7.11 | `git ls-files -u` is the documented resolution test: "After resolving conflicts and staging the result, `git ls-files -u` would stop mentioning the conflicted path."                                                                                                                                                                 | HARD     | `git-commit(1)`                                                                                     |
| 3.7.12 | `git rebase --quit` differs from `git merge --quit`: it leaves `HEAD` un-reset as well — "HEAD is not reset back to the original branch. The index and working tree are also left unchanged."                                                                                                                                         | HARD     | `git-rebase(1)`                                                                                     |
| 3.7.13 | GAP: nothing documents what `git rebase --continue`, `git cherry-pick --continue` or `git revert --continue` do with the index, or whether unstaged changes are folded in. Only the merge case is documented.                                                                                                                         | GAP      | searched `git-rebase(1)`, `git-cherry-pick(1)`, `git-revert(1)` for index behaviour on `--continue` |
| 3.7.14 | GAP: `git-add(1)` never mentions merges, conflicts or unmerged entries at all; the "add marks resolved" contract lives only in `git-merge(1)`, `git-commit(1)` and `git-rebase(1)`. `git-rm(1)` likewise documents no role in resolving a delete conflict.                                                                            | GAP      | grepped both pages for `merge`, `conflict`, `resolv`                                                |

**Findings 3.7.2, 3.7.7, 3.7.8 and 3.7.9 together are the basis of FR-017c, and they refine it in a way worth stating precisely**, because two of them cut against the obvious reading.

Concluding commits the whole index and **cannot** be narrowed to pathnames — 3.7.8 says git refuses outright. So "commit only the conflicted paths" is not achievable by limiting the commit; it is achievable only by controlling what is in the index when the commit happens. Two facts make that tractable. Git has already staged the cleanly-merged paths itself (3.7.7), and those _are_ part of the operation rather than unrelated work, so they belong in the commit. And pre-existing local modifications are left unstaged, matching `HEAD` (3.7.9), so ordinary dirty work is not at risk.

What remains at risk is narrow and real: a path the user had **already staged** before the operation began, or anything the skill itself stages beyond the resolution. The first is partly guarded by git's own pre-merge check (3.7.10) but not eliminated — a staged change to a file the merge does not touch survives into the concluding commit. So FR-017c becomes concrete as: stage with `git add <path>` per resolved path, never `git add -A`, never `git add .`, never `git commit -a`; report any pre-staged unrelated path to the user **before** concluding rather than silently committing it; and use 3.7.11's `git ls-files -u` as the check that a path is actually resolved. `unrelated_dirty_paths` is captured before any resolution precisely so this comparison can be made, which is SC-006a.

Finding 3.7.13 is an honest limit on how confidently the skill can behave outside the merge case. For rebase, cherry-pick and revert, git does not document what `--continue` does with the index, so the skill applies the same staging discipline and does not claim a guarantee the documentation does not give.

Finding 3.7.5 also matters for the abort option: `--abort` is the one that restores the pre-merge state, and it is what `mechanism: abort-operation` uses. `--quit` looks adjacent in a help listing and would leave a half-resolved tree with no operation in progress — and under rebase (3.7.12) it additionally leaves `HEAD` detached mid-replay, which is worse still.

### 3.8 Safety and recovery

| #      | Finding                                                                                                                                                                                                                                                                                                                 | Strength | Source                                                                                      |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------- |
| 3.8.1  | Declining to merge requires resetting the index to `HEAD` and cleaning working-tree changes; `git merge --abort` does both.                                                                                                                                                                                             | HARD     | `git-merge(1)`                                                                              |
| 3.8.2  | `ORIG_HEAD` records the previous position of `HEAD` before an operation that moves it, giving a recovery point.                                                                                                                                                                                                         | HARD     | `git-rev-parse(1)`                                                                          |
| 3.8.3  | **`git merge --abort` is not a guaranteed undo**: "If there were uncommitted worktree changes present when the merge started, `git merge --abort` **will in some cases be unable to reconstruct these changes.** It is therefore recommended to always commit or stash your changes before running `git merge`."        | HARD     | `git-merge(1)`                                                                              |
| 3.8.4  | `git reset --merge` is the documented conflict-safe reset, and "mainly exists to reset unmerged index entries"; it keeps changes that are different between the index and working tree. `git reset --hard` by contrast "may overwrite untracked files".                                                                 | HARD     | `git-reset(1)`                                                                              |
| 3.8.5  | The two documented undo-a-merge recipes differ in exactly this respect: `git reset --hard ORIG_HEAD` "will discard your local changes, which you do not want", while `git reset --merge ORIG_HEAD` "keeps your local changes".                                                                                          | HARD     | `git-reset(1)`                                                                              |
| 3.8.6  | `git checkout --force` is documented as being "used to throw away local changes and any untracked files or directories that are in the way".                                                                                                                                                                            | HARD     | `git-checkout(1)`                                                                           |
| 3.8.7  | `git fsck --lost-found` writes dangling objects to `.git/lost-found/`, and critically: "**If the object is a blob, the contents are written into the file, rather than its object name.**" That clause is what makes it usable for recovering a lost resolution, which is a blob rather than a commit.                  | HARD     | `git-fsck(1)`                                                                               |
| 3.8.8  | `git merge --autostash` carries its own warning: "use with care: the final stash application after a successful merge might result in non-trivial conflicts."                                                                                                                                                           | HARD     | `git-merge(1)`                                                                              |
| 3.8.9  | GAP: git's documentation does not offer a recovery path for a hand resolution that was never staged or committed. Nothing records it, so `git checkout --merge` (3.6.2) or `--abort` discards it. Reflog, `ORIG_HEAD` and `--lost-found` are each documented in isolation; no page ties them into a recovery procedure. | GAP      | searched `git-merge(1)`, `git-checkout(1)`, `git-rerere(1)`, `git-reflog(1)`, `git-fsck(1)` |
| 3.8.10 | GAP: `git-reset(1)` contains no explicit statement that `--hard` destroys work irrecoverably, and `git stash drop`'s entire documented description is "Remove a single stash entry from the list of stash entries" — no data-loss warning on either.                                                                    | GAP      | grepped both pages for `lose`, `unrecoverab`, `irrevers`, `destroy`                         |

**Finding 3.8.9 is the sharpest safety point for `docs/merge-conflict-practices.md`**, and it is why FR-016 forbids the skill discarding uncommitted work: an unstaged hand resolution has no reflog entry and no rerere record. It exists only in the working tree, and any command that re-materialises the conflict destroys it. 3.8.7 is the partial escape hatch — a blob that was staged at some point can be dug out of `--lost-found` — but a resolution that was never staged was never an object, so nothing can recover it.

**Finding 3.8.3 changes what the skill may promise.** An earlier draft of the abort option would have described it as returning the tree to how it was found. Git does not guarantee that when uncommitted changes were present at the start, so the skill's abort option says what git says: it reconstructs the pre-merge state, and where uncommitted changes were present that reconstruction may be incomplete. Overstating it would be the more dangerous error, because the user chooses abort precisely when they want a way back.

Findings 3.8.4 through 3.8.6 are the commands the skill must **never** reach for, and 3.8.10 explains why they need naming explicitly: git's own pages do not warn about them in the terms a reader would expect, so a contributor reading the manual is not warned off. `docs/merge-conflict-practices.md` states the prohibition directly.

### 3.9 Reducing and avoiding conflicts

Not needed to resolve the conflict in front of you, and the most useful part of the subject for a reader who keeps hitting the same one. Recorded briefly and cited, so `docs/merge-conflict-practices.md` can point somewhere real.

| #      | Finding                                                                                                                                                                                                                                                                                                                                                                                            | Strength | Source                                                    |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | --------------------------------------------------------- |
| 3.9.1  | `merge.renormalize` and `-Xrenormalize` convert data "to a canonical form before performing a merge **to reduce unnecessary conflicts**" — aimed at branches with differing clean filters or line-ending rules.                                                                                                                                                                                    | HARD     | `git-config(1)`, `git-merge(1)`                           |
| 3.9.2  | `-Xignore-space-change`, `-Xignore-all-space`, `-Xignore-space-at-eol` and `-Xignore-cr-at-eol` treat whitespace-only changes as unchanged for the three-way merge, with documented tie-breaks in both directions.                                                                                                                                                                                 | HARD     | `git-merge(1)`                                            |
| 3.9.3  | `-Xdiff-algorithm=histogram` and friends "can help avoid mismerges that occur due to unimportant matching lines (such as braces from distinct functions)". | 3.9.4  | `merge.renameLimit` defaults to 7000 via `diff.renameLimit`, and has no effect when rename detection is off. | 3.9.6  | A custom merge driver is defined in config rather than in `.gitattributes`, receives `%O %A %B %L %P`, must leave its result in `%A`, and must exit non-zero on conflict — with an exit above 128 treated as a **failure** rather than a conflict.                                                                                                                                                 | HARD     | `gitattributes(5)`                                        |
| 3.9.7  | `git rebase --update-refs` force-updates branches pointing at rebased commits, but "any branches that are checked out in a worktree are **not** updated in this way." Introduced in Git 2.38.0.                                                                                                                                                                                                    | HARD     | `git-rebase(1)`, release notes 2.38.0                     |
| 3.9.8  | `zdiff3` was introduced in **Git 2.35.0** — "\"Zealous diff3\" style of merge conflict presentation has been added."                                                                                                                                                                                                                                                                               | HARD     | release notes 2.35.0                                      |
| 3.9.9  | A documented three-way-merge surprise no setting fixes: "if a change is made on both branches, but later reverted on one of the branches, that change will be present in the merged result; some people find this behavior confusing. It occurs because only the heads and the merge base are considered."                                                                                         | HARD     | `git-merge(1)`                                            |

| 3.9.11 | GAP / documentation inconsistency: `merge.default` is referenced by `gitattributes(5)` but is absent from `git-config(1)`.                                                                                                                                                                                                                                                                         | GAP      | grepped `git-config(1)` for `merge.default`               |

Finding 3.9.8 sets a floor for the `zdiff3` recommendation: it is only available from Git 2.35.0, so `docs/merge-conflict-practices.md` names the version rather than recommending it unconditionally.

Finding 3.9.10 is the distinction most likely to cause real damage among the ones in this section — `-s ours` discards the other side's work entirely, `-Xours` does not — and it is why the skill never offers a strategy-level option in its candidate resolutions. Every resolution it proposes acts on one path, where the effect is visible and reversible, rather than on the whole merge.

### 3.10 What was deliberately not pursued

- **`git merge-tree`** as a preview mechanism. It is the true no-side-effect preview (3.3.5, and its exit status is 1 on conflict), and it is not needed here: the skill operates on a conflict that already exists or one the user approved creating, so a preview would add a step without changing a decision.
- **`git mergetool`'s full configuration surface** — `mergetool.<tool>.cmd` with its `BASE`/`LOCAL`/`REMOTE`/`MERGED` contract, `trustExitCode`, `keepBackup`, `hideResolved`. The skill offers `git mergetool` as a candidate mechanism and does not configure it; a user's tool choice is theirs.
- **Submodule conflicts.** rerere cannot track them, and resolving them correctly means reasoning about another repository's history. Out of scope, and named so a later reader knows it was a decision.
- **`git bisect`.** `BISECT_HEAD` exists only in `--no-checkout` mode and a bisect is not a conflict-producing operation in the sense the spec means.

These are named rather than silently dropped, following the same convention as the gaps above.
